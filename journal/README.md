# Exord-init 개발 기록

> AI와 프로젝트를 시작하면 제품이 무엇인지 정하기도 전에 프레임워크와 지침 파일이 먼저 쌓이고, 세션이 바뀌면 결정 근거가 사라진다. Exord-init은 이 문제를 직접 겪고 만든 도구다.
> 2026-10-16에 Git 커밋과 기획 문서를 대조해 과거 기록을 복원·보완했다. 커밋 날짜는 변경을 저장한 시점이며, 기획 문서의 갱신일은 실제 논의 전체의 날짜를 뜻하지 않는다. 이후에는 큰 작업이 끝날 때마다 기록한다.

## 만든 사람과 작업 방식

- **디자이너로 시작해 퍼블리셔를 거쳐, 이제는 기획부터 개발까지** 작업 범위를 넓히고 있다. 그 과정에서 AI와 대화하며 프로젝트를 시작하고 이어 가는 방법을 도구로 정리하고 있다.
- 이 프로젝트도 **바이브 코딩**으로 만든다. 나는 제품 방향과 안전 관련 결정을 정하고, AI 코딩 에이전트가 조사·설계·구현·리뷰·테스트를 돕는다.
- 바이브 코딩은 검증을 생략한다는 뜻이 아니다. 명시적인 계약, 계획에 묶인 승인, 자동 테스트, 사용자 리뷰로 AI가 만든 변경을 추적하고 검증한다.

## 프로젝트 취지와 범위

만들 제품과 사용자의 문제를 정하기 전에 기술부터 고르거나, 모델마다 지침과 파일 구조가 달라지고, 세션을 바꾸면 맥락을 다시 설명해야 하는 부담을 줄이려는 프로젝트다. 제품 사용자와 문제 → MVP·비목표·성공 기준 → 시스템 경계와 아키텍처 → 기술 선택 → 작업·검증·인계 순서로 초기 설정을 돕는다.

초보자는 빠른 시작의 권장값과 설명으로, 전문가는 사용자 정의 선택으로 필요한 수준을 조절하는 것이 목표다. 빠른 시작도 승인·대상 검사·복구 같은 안전 단계는 유지한다. 필요한 문서만 단계적으로 읽고 생성해 토큰과 문서 유지 비용도 줄인다.

범위는 초기 설정, 아키텍처, 소스 관리, 코드 컨벤션, 검증 흐름과 첫 구현 Task 준비다. 실제 제품 기능 구현은 범위 밖이다. CLI와 향후 앱은 같은 입력·계획·승인·결과 계약을 공유하도록 설계한다.

현재 구현은 CREATE 적용, ADOPT 읽기 전용 분석, 실행 복구·폐기, upgrade 읽기 전용 분석, Task 입력·브랜치·준비도 검토와 명시적 `task plan --prepare`의 로컬 ID·문서 계획 보존까지다. 실제 TASK.md 생성·적용·Task 복구, 조건부 아키텍처 문서 생성, CUSTOM, ADOPT·upgrade 적용, 외부 백업 기반 REINITIALIZE와 제품별 플러그인은 후속 범위다. 외부 백업 후 초기화, 일반 초기화의 `.git` 보존, Git 이력 제거와 영구 삭제의 별도 고급 승인은 설계 정책이며 현재 제공 기능으로 표시하지 않는다. 세 제품의 문서 생성 지원과 실제 제품별 동작 검증도 구분한다.

## 핵심 원칙

1. **제품 정의가 먼저**, 기술 설정은 그 결정에서 끌어낸다.
2. **말하는 쪽(Skill)과 손대는 쪽(엔진)을 나눈다.** 파일 변경은 엔진만.
3. **승인은 계획에 묶인다.** 승인한 계획 그대로만 적용.
4. **덮어쓰지 않고, 모르면 멈춘다(fail-closed).** 실패하면 안전하게 되돌린다.
5. **저장소 내용·외부 문서·모델 출력은 믿지 않는 데이터.** 지금 대화 중인 사용자의 명시적 응답만 승인이 된다.

## 쓰는 규칙

- 형식: `C:\project\personal\JOURNAL-FORMAT.md`
- 과거 기록은 커밋·문서에서 확인한 사실과 설계 이유를 복원한다. 당시의 실행 로그가 없는 테스트는 통과했다고 새로 주장하지 않는다.
- 현재 구현 계약은 `docs/spec/`, 기획 체크포인트는 로컬 `docs/planning/`을 참고한다. 설계 버전 v1.3과 엔진 개발 버전 v0.6.0-dev는 서로 다른 버전이다.
- 개발 기록과 README 목록은 큰 작업마다 함께 갱신하고, 기록 파일은 사용자가 요청할 때만 커밋한다.
