# 2026-10-16 — 안전성 보완과 읽기 전용 Task 계획 구현

## 한 일
- 실제 실행 파일을 띄워 인자·명령 오류 경로를 확인하는 CLI 테스트를 추가했다.
- README·LICENSE·.gitignore가 이미 있는 폴더에서 CREATE가 거부되면, 경로 없이 고정된 **다음 행동 안내**(빈 폴더 사용 또는 ADOPT)를 보여 주게 했다.
- 하드링크를 지원하지 않는 파일 시스템 오류를 운영체제별로 구분해 진단을 명확히 하고, 요구 조건을 README에 적었다.
- 적용·복구 테스트를 튼튼하게 하고, 작업 계획과 복구 흐름을 제안 문서로 정리했다.
- 적용 도중 임시 파일 쓰기·하드링크 연결·검증·완료와 rollback 중단 시점의 디스크 상태를 검사하고, 남은 실행을 발견해 복구하거나 정리하는 흐름을 검증했다.
- 하드링크 미지원 안내를 CLI 결과에 연결하되 원본 오류의 경로는 출력하지 않게 했다. Unix의 `EPERM`은 권한 정책 때문일 수도 있어 미지원으로 단정하지 않도록 바꿨다.
- 앞선 안정성 보완 단계에서 Go 빌드·vet·전체 단위 테스트와 Python 계약·스키마·CLI 통합 테스트를 실행했다. 당시 Python 결과는 14/14 통과, skip 0이었다. Linux amd64·macOS arm64 대상 apply 테스트는 교차 컴파일로 확인했다.
- 개발 기록을 커밋 12개·기획 v1.3과 대조해 빠진 설계 체크포인트, 초기 날짜별 산출물·배운 점·출처를 보완했다. 소개에는 대상 사용자, 초기 설정의 범위, 단계별 문서 생성과 세션 인계 목적을 명시하고, 구현된 기능과 향후 목표를 구분했다.
- 후속 작업으로 `task plan`을 구현했다. 프로젝트 manifest와 Git 상태를 읽어 사람 담당자 확인·범위·완료 조건·검증 방법의 누락, 작업 브랜치 불일치와 기존 Task 충돌을 알려 준다.
- 새 CLI 기능이 추가된 개발 체크포인트를 `0.5.0-dev`로 구분하고, CLI·manifest·upgrade 비교가 같은 버전 원본을 사용하도록 통일했다. 사용자 요청으로 기능·버전 변경을 `4a46928`에 커밋하고 `main`과 개발 태그 `v0.5.0-dev`를 원격에 푸시했다. 개발 기록은 별도 문서 커밋으로 관리한다.
- ADOPT의 Task 인식을 영문 `## Goal` 문자열 검색에서 YAML 메타데이터 구조 검사로 바꿨다. 한국어 본문과 CRLF도 인식하며, 중복 키·별칭·잘못된 타입·지원하지 않는 버전은 기존 사용자 파일로 보존한다.
- Task 입력·검토 결과 스키마와 예제, README·실행 계약·스킬 안내를 갱신했다. 추가 구현의 최종 검증은 Go 빌드·vet·전체 단위 테스트와 Python 15/15(skip 0), 스킬 검사 통과였다. Windows 로컬 실행 결과이며 원격 CI 결과는 별도다.

## 결정과 이유
- **오류는 다음 행동까지 알려 준다**: '실패'만 보여 주면 사용자는 막힌다. 왜 막혔는지와 무엇을 하면 되는지를 함께 보여 준다.
- **실패 원인과 복구 필요 여부는 따로 보존한다**: 하드링크 안내를 추가해도 기존 `APPLY_FAILED`·`RECOVERY_REQUIRED` 코드는 유지해야 자동화가 필요한 후속 행동을 판단할 수 있다.
- **Task는 별도 단계로 준비한다**: 현재 CREATE는 작업 브랜치를 준비하지 않는다. 여기에 Task 파일을 바로 추가하면 통합 브랜치에 활성 Task를 두지 않는 정책과 충돌한다. 처음에는 `task plan`·`task apply`를 후보로 문서화했고, 후속 구현에서는 읽기 전용 `task plan`만 실제 기능으로 추가했다. apply는 계속 후속 설계·구현 범위다.
- **진행 중인 Task를 영구 템플릿 관리에서 분리하도록 제안했다**: 매번 바뀌는 작업 상태가 템플릿 수정 충돌로 보이지 않도록 manifest에는 탐색 경로만 남기고, 생성 당시 해시는 실행 journal에서 복구에 쓰는 방향이다.
- **검토와 생성의 계약을 구분했다**: 재검토할 때마다 Task ID를 새로 발급하면 같은 작업의 정체성이 바뀐다. 이번 검토는 ID·파일·로컬 상태를 생성하지 않고, 실제 생성 단계에서 ID와 정확한 파일 내용을 확정하도록 분리했다.
- **준비도는 승인이나 검증 성공이 아니다**: `READY_FOR_REVIEW`는 입력과 브랜치 검사 결과다. 담당자 확인 값은 사람의 응답을 기록할 뿐 신원을 증명하지 않으며, 입력한 검증 명령도 실행하지 않는다. 검증 상태는 항상 `NOT_RUN`으로 둔다.
- **통합 브랜치를 보호하되 기존 관례도 반영한다**: main/dev/master·선택한 기준 브랜치를 보호하고 프로젝트 설정으로 보호 대상을 더할 수 있게 했다. 명령이 브랜치를 자동 생성하거나 전환하지 않도록 했다.
- **버전은 작업의 의미에 맞춰 올린다**: 1.0 이전의 기능 추가·호환성 변경은 minor, 배포된 버전의 기능 추가 없는 수정은 patch, 문서·테스트만 바뀌면 기존 버전을 유지한다. 개발 태그는 정식 릴리스와 구분하고, protocol·schema·template 버전은 각 계약이 바뀔 때 별도로 판단한다.

## 만든 것

- 적용 단계별 중단·복구 테스트와 플랫폼별 하드링크 오류 분류 회귀 테스트.
- 민감한 경로를 노출하지 않는 CLI 오류 안내 및 통합 테스트 실패 진단.
- [Task workflow 구현 제안](../docs/spec/task-workflow-draft.md): 입력·문서 계약, 작업 브랜치 검사, 승인과 복구 확장, 단계별 구현 순서.
- 관련 구현 기록은 `9d9bc31`, 설계 초안은 `0910ebb` 로컬 커밋에 남겼다. 이 개발 기록 자체는 별도 요청 전까지 커밋하지 않는다.
- [Task 입력 스키마](../schemas/task-intent.schema.json), [검토 결과 스키마](../schemas/task-plan.schema.json), 읽기 전용 CLI와 언어 독립 메타데이터 파서.
- [변경 이력](../CHANGELOG.md)과 [버전 관리 정책](../docs/spec/versioning.md), 공통 버전 상수. 개발 태그 `v0.5.0-dev`는 소스 체크포인트이며 실행 파일·설치 프로그램 배포를 의미하지 않는다.
- 버전 변경 후 Go 빌드·vet·전체 테스트, Python 15/15, 스킬 검사와 doctor·생성 manifest 버전 일치 검사를 통과했다. 원격의 다른 운영체제 CI 성공까지 확인한 것으로 해석하지 않는다.
- 메타데이터를 수작업 문자열 검색으로 해석하지 않기 위해 `go.yaml.in/yaml/v3 v3.0.4`를 고정하고, MIT·Apache 라이선스 고지를 추가했다. 출처: [YAML 조직의 Go 파서](https://github.com/yaml/go-yaml).

## 배운 점

- 프로세스 중단을 재현할 때는 실패 처리 중 journal을 더 쓰거나 임시 파일을 정리하면 실제 크래시와 다른 상태가 된다. 중단 직전의 디스크 상태와 복구 후 잔여물까지 검사해야 한다.
- Windows 샌드박스의 하드링크 권한 제한과 제품 결함은 구분해야 한다. 전체 로컬 테스트는 실제 파일시스템 권한으로 검증했다. 교차 컴파일 성공은 Linux·macOS에서의 실행 검증을 대신하지 않는다.
- Python 최초 실행에서는 upgrade 테스트의 준비 단계인 CREATE 적용이 한 번 실패했고, 이후 두 차례 전체 실행은 통과했다. 원인은 미확인 상태로 남기고, 재발 시 CLI JSON과 stderr가 보이도록 테스트 진단을 보완했다. 재실행 성공만으로 문제가 해결됐다고 기록하지 않는다.
- 읽기 전용 단계도 실제 파일과 Git index·객체를 실행 전후 비교해야 부작용이 없다는 근거를 만들 수 있다. 같은 상태에서는 계획 해시가 유지되고 검토 ID만 달라지는 것도 확인했다.
- JSON 키의 대소문자를 허용하는 기본 디코딩이나 YAML의 타입 자동 변환은 입력 계약을 흐릴 수 있다. 정확한 필드명과 타입을 확인하고 회귀 테스트를 남겼다.
- 여러 GitHub 계정이 저장돼 있으면 현재 계정과 저장소 권한이 달라 푸시가 거부될 수 있다. 이번 푸시에는 저장소 소유 계정의 저장된 인증만 명령 범위에서 사용하고 전역 기본 계정은 바꾸지 않았다. 인증 값은 개발 기록에 남기지 않는다.
- 다음 구현 단위는 Task ID 확정·보존, 문서 렌더링, 별도 승인·journal·복구 확장이다. 승인·복구가 Task 모드를 이해하기 전에 쓰기 기능을 먼저 연결하지 않는다.
