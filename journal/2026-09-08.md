# 2026-09-08 — 설계 기준 정리

> 2026-10-16에 로컬 기획 v1.3의 최종 갱신일을 기준으로 복원했다. 여러 차례 논의가 누적된 체크포인트이며, 모든 결정을 이 날짜에 했거나 구현을 마쳤다는 의미는 아니다.

## 한 일

- 개인과 팀, 바이브 코딩 초보자와 전문가를 위한 초기 설정 도구의 목적과 경계를 정리했다.
- 실행 목적 CREATE·ADOPT·REINITIALIZE와 질문 깊이 QUICK·CUSTOM을 독립된 축으로 설계했다.
- 제품 정의에서 기술 선택을 도출하고, 필요한 문서만 생성·탐색하는 흐름을 정리했다.
- 작업 브랜치의 활성 Task, 담당자, 검증, 인계와 완료 이력의 책임을 나눴다.
- 대화형 Skill과 Go 엔진, JSON 계약, 배포·라이선스와 단계별 구현 순서를 정리했다.

## 결정과 이유

- **공통 규칙은 짧게 유지한다**: AGENTS.md를 기준으로 제품별 연결 파일은 얇게 두고, 하위 폴더마다 같은 규칙을 복제하지 않는다. 아키텍처 계층 문서는 필요가 생길 때만 만든다.
- **Task는 현재 맥락에 집중한다**: 루트 TASK.md 하나를 작업 브랜치에서 사용하고, 영역은 메타데이터로 표현한다. 완료 이력은 PR·commit·CI에 남겨 영구 archive와 수동 index의 중복 관리를 피한다.
- **기존 프로젝트를 먼저 보호한다**: 일반 재초기화는 외부 백업과 검증을 기본으로 하고 `.git`을 보존한다. 영구 삭제와 Git 이력 제거는 별도 고급 승인으로 분리한다. 이 기능은 안전 기반을 검증한 뒤 구현한다.
- **모델 간 일관성은 실행 계약에서 얻는다**: Skill이 의도를 정리하고 엔진이 대상 검사·작업 목록·해시·검증 결과를 생성한다. CLI와 앱도 같은 계약을 사용하고, 소스 코드의 완전한 일치보다 같은 계약과 검증 결과를 목표로 한다.
- **빠른 시작도 안전 단계를 유지한다**: 질문과 설명은 줄일 수 있지만 승인과 위험 검사는 생략하지 않는다. 저장소나 외부 문서에 적힌 지시를 사람의 승인으로 취급하지 않는다.

## 만든 것

- 로컬 기획·설계 v1.3 체크포인트와 변경 결정 목록. 근거: `docs/planning/exord-init-planning-design-v1.3.md`.
- 코드는 Apache-2.0, 생성 템플릿은 CC0로 구분하는 설계와, 읽기 전용 계획부터 쓰기·복구·고위험 초기화 순으로 확장하는 구현 기준.

## 배운 점

- 범위가 넓은 초기화 도구는 문서를 많이 만드는 것보다 무엇을 언제 생성할지 정하는 일이 먼저다.
- 승인·백업·복구는 실패 후 붙이는 부가 기능이 아니라 계획·상태·파일 소유권 설계에 함께 들어가야 한다.
- 체크포인트는 당시 설계를 보존한다. 이후 구현 진척은 실행 사양과 커밋으로 대조해야 설계 완료와 기능 완료를 혼동하지 않는다.
