# 2026-09-09 — v0.2 기반과 ADOPT 분석

## 한 일
- **v0.2 기반**: 대화를 맡는 Agent Skill(`SKILL.md`)과 파일 작업을 맡는 Go 엔진을 나눈 구조를 만들었다.
- 프로젝트 안내 문서와 공개 모듈 경로를 정리했다.
- **한국어 안내 문서와 바이브코딩 공개 문구**를 추가했다.
- 기존 프로젝트를 건드리지 않고 무엇이 있는지, 무엇이 충돌하는지 보여 주는 **읽기 전용 ADOPT 계획**을 만들었다.

## 결정과 이유
- **순서를 바꾼다**: 기술 스택부터 고르지 않고 제품 정의 → 범위 → 아키텍처 경계 → 협업 규칙 → 소스 관리 → 검증 → 작업 준비 순서로 정하고, 기술 설정은 그 결정에서 끌어낸다.
- **말하는 쪽과 손대는 쪽을 나눈다**: 대화형 Skill은 선택지와 장단점을 설명만 하고, 실제 파일 변경·해시·기록은 결정적으로 동작하는 엔진만 한다. AI가 임의로 파일을 만지지 못하게 하기 위해서다.
- **바이브코딩임을 밝힌다**: AI가 만든 변경이라는 것을 숨기지 않고, 대신 계약·승인·자동 테스트·사용자 리뷰로 검증한다고 명시했다.

## 만든 것

- doctor, CREATE + QUICK 계획과 승인형 apply, 파일 해시·실행 journal·rollback을 포함한 Go 기반. 근거: `e353266`.
- 공통 SKILL.md, 제품별 연결 문서, 영어·한국어 AGENTS·PROJECT 템플릿과 JSON Schema.
- 프로젝트 안내·공개 모듈 경로·한국어 README·바이브 코딩 공개 문구. 근거: `dcdb899`, `b6715e4`.
- 기존 파일·Git·Task·충돌·비밀 가능성을 분석하는 읽기 전용 ADOPT. 근거: `bdd76ce`.
- 코드 Apache-2.0과 템플릿 CC0의 라이선스 구분.

## 배운 점

- 대상이 비어 있는지와 기존 파일의 소유권을 확인해야 새 프로젝트 생성과 기존 프로젝트 도입을 안전하게 나눌 수 있다.
- ADOPT의 읽기 전용은 대상 프로젝트 기준이다. 안정적인 project ID를 위해 대상 밖 사용자 상태 경로에는 로컬 메타데이터를 만들 수 있으므로 이 차이를 설명해야 한다.
- 세 제품용 문서를 만들었다는 사실만으로 실제 세 제품의 동작 호환성이 검증되는 것은 아니다. 엔진 계약 테스트와 제품별 실행 검증은 별도다.
