# 2026-09-11 — 정리 명령과 업그레이드 분석

## 한 일
- **recover discard**: 끝난(실패·완료·미적용) 실행 기록 하나를, 그 실행에 묶인 별도 승인을 받아 지운다. 복구가 필요한 기록은 지울 수 없고, 한 번에 여러 개를 지우는 기능은 일부러 만들지 않았다.
- **plan --upgrade**: 이미 exord-init으로 만든 프로젝트를 업그레이드하면 파일마다 무엇이 일어날지(최신 / 템플릿 갱신 가능 / 사용자가 고친 파일 검토 / 누락 재생성 등) 보여 준다. 대상은 건드리지 않는다.

## 결정과 이유
- **지우는 기능은 가장 좁게**: 증거가 될 수 있는 기록을 실수로 한꺼번에 지우지 않도록, 한 건씩, 끝난 것만, 별도 승인으로만 지우게 했다.
- **바꾸기 전에 보여 준다**: 업그레이드는 실제 적용보다 '무엇이 바뀔지'를 먼저 보여 주는 분석부터 만들었다.

## 만든 것

- 승인 결합 recover discard와 settled run 판정·거부·스키마 테스트. 근거: `52e0653`.
- manifest·baseline·현재 파일·템플릿 버전 비교, 파일별 upgrade action과 전체 disposition을 반환하는 plan --upgrade. 근거: `6ea75d7`.
- 로컬 수정·누락·새 관리 파일·고아 관리 파일·downgrade·알 수 없는 hash mode의 분류 테스트와 관련 문서.

## 배운 점

- 실행 번들 폐기와 대상 프로젝트의 파일 정리는 서로 다르다. recover discard가 있어도 완료된 프로젝트나 잔여 디렉터리를 자동 정리하는 기능까지 제공하는 것은 아니다.
- 관리 파일의 기준 해시와 사용자 수정 여부를 분리해야 업그레이드가 사용자의 변경을 덮어쓰지 않는다. 이날 구현 범위는 분석이며 upgrade apply는 후속 작업이다.
- 2026-09-11 로컬 점검에서는 Go 검증과 Python 계약·스키마·CLI 통합 테스트 14개가 모두 통과했다. 이 결과는 Windows amd64 기준이며 원격 CI 전체 결과를 뜻하지 않는다.
