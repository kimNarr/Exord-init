## 한 일

- 전날 준비한 `task plan --prepare`와 한영 문서·스키마·로컬 상태 저장 변경을 검토했다. 일반 `task plan`은 읽기 전용이고 준비 모드도 실제 TASK.md를 만들지 않는다.
- Git 출력 제한 버퍼의 임베딩으로 `io.Copy`가 제한된 `Write` 대신 승격된 `ReadFrom`을 호출할 수 있는 문제를 수정하고 회귀 테스트를 추가했다.
- 지원하지 않는 미래 journal 버전을 만나면 기존 엔진이 실행을 무시하지 않고 차단하는 테스트를 추가했다.
- Windows 로컬 통합 테스트 최초 실행에서 기존 CREATE 준비 단계의 간헐적 적용 실패를 다시 관찰했다. 원인을 확정하지 않았으며, 상태 파일 원자적 교체 실패를 경로 노출 없이 구분하도록 진단만 보완했다.
- Go 빌드·vet·전체 테스트, Python 15/15(skip 0), 스킬 검사와 diff 공백 검사를 통과했다. 최종 진단 보완 후 상태·CLI Go 테스트와 전체 Python·스킬 검사도 재실행해 통과했다. CREATE 적용·크래시 복구의 관련 테스트는 20회 반복 통과했지만 간헐적 문제 해결을 의미하지 않는다.
- 사용자 승인에 따라 `49167b0`으로 커밋·푸시했다. [해당 커밋의 CI](https://github.com/kimNarr/Exord-init/actions/runs/38999334311)에서 Linux amd64·arm64, Windows amd64, macOS arm64의 빌드·vet·Go 테스트·Python 통합 검증이 모두 성공했다. 이 검증된 소스에 개발 태그 `v0.6.0-dev`를 연결하며, 실행 파일이나 설치 프로그램을 배포하는 단계는 아니다.

## 결정과 이유

- **미리보기와 실행 승인은 별도다**: 보존한 문서나 담당자 확인을 승인으로 취급하지 않는다. 정확한 계획·바이트·대상 상태에 묶인 Task 생성 전용 승인이 필요하다.
- **이전 엔진도 새 실행을 발견해야 한다**: Task 전용 디렉터리로 실행을 숨기는 대신 공통 runs 탐색과 명시적인 새 journal 버전을 쓰는 안을 제안했다. 구버전은 해석하지 못하면 멈춰야 한다.
- **복구는 사용자의 후속 작업을 지우지 않는다**: Task가 수정·stage·commit되었거나 브랜치 상태가 바뀌면 자동 삭제하지 않는 방향이다. Git reset이나 자동 브랜치 전환은 하지 않는다.
- **초안과 구현을 혼동하지 않는다**: 승인·journal·Task 복구 계약은 DRAFT이며 기능·명령·스키마 구현이나 capability 추가로 표시하지 않는다. 해당 계약 검토 후 단계별로 구현한다.

## 만든 것

- 로컬 ID·불변 문서 계획 보존 기능, 영문·한국어 TASK 템플릿과 검증 스키마.
- 출력 크기 제한 스트림 복사 회귀 테스트, 미래 journal 차단 테스트, 민감 경로 없는 상태 교체 오류 분류.
- [Task 승인·적용·복구 계약 초안](../docs/spec/task-apply-contract-draft.md).
- [0.6.0-dev 변경 이력](../CHANGELOG.md)과 프로젝트 소개·날짜별 기록 목록 갱신.

## 배운 점

- 스트림 크기 제한은 `Write`만 검사해서 충분하지 않다. Go의 메서드 승격과 `io.Copy`의 빠른 경로까지 검증해야 한다.
- 재실행 성공은 간헐적 실패의 원인 규명이나 해결이 아니다. 관찰과 진단 개선, 검증 통과 범위를 구분해 남긴다.
- 미래 포맷을 추가하기 전에 이전 엔진의 탐색·차단 동작부터 확인해야 실행 상태가 버전 사이에서 사라지지 않는다.
