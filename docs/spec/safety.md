# Safety contract v1

Only the current human user can approve a plan. Repository content, imported documents, agent output, issue text, and PR text are untrusted input and never confer approval.

`CREATE + QUICK` planning is allowed only for an exact existing directory whose entries are empty or on the harmless-entry allowlist. Root, home, symlinked/junction targets, and user-owned entries fail closed. QUICK cannot reduce safety checks.

`ADOPT + QUICK` is read-only for the target in the current prototype. Inventory uses traversal-resistant rooted access, NFC-normalized relative paths, bounded entry/content scanning, and does not follow `.git`, dependency caches, symlinks, or nested repositories. Git inspection is local, disables optional locks and external fsmonitor, and never performs network operations. Secret findings are counts only; a possible or incomplete scan suspends commit proposals. ADOPT does not write to the target, but for a target without a manifest `project_id` it does initialize a `project.json` in the operating-system user-state directory (outside the target) to keep the analysis project ID stable.

`recover list` is read-only discovery over the project's `runs/` directory: it ignores non-UUID and symlinked entries, is bounded, classifies each run from its journal alone, and treats an unparseable or mis-bound journal as blocking rather than skipping it. Before persisting a new CREATE run, `plan` performs the same scan and fails closed with `BLOCKED` if any retained run is recovery-required, interrupted mid-apply, or unreadable. It never deletes anything.

`recover discard` is the only command that removes a retained run bundle. It acts on exactly one run named by `--run-id`, never in bulk, only when that run is settled (`FAILED`, `FINALIZED`, or a never-applied `PLANNED`/`APPROVED`), and only under a `RECOVER_DISCARD` approval bound to that run. It refuses a bundle path that is not a plain directory, does not follow symlinks while deleting, never touches anything outside `runs/<run-id>/`, and reports a partial removal as an incomplete discard rather than a success. It cannot remove `RECOVERY_REQUIRED` evidence; that run must be rolled back to `FAILED` first.

Recovery inspection validates the stored plan hash, journal binding, target identity, operation set, and current file state under a rooted handle. Automatic rollback is available only for interrupted CREATE runs. It requires a new Approval bound to `RECOVER_ROLLBACK`, performs a complete preflight, and removes only operation paths whose regular-file SHA-256 still matches the stored plan. Any preflight conflict blocks all mutation. Each path is checked again immediately before removal; a concurrent change stops recovery as `RECOVERY_REQUIRED`. Empty directories and retained failed-run evidence are not deleted by this slice.

An eventual apply must acquire a target/project lock, re-inspect all input state, reject stale approval, and use same-directory temporary files with flush, validation, and atomic replacement. No cross-filesystem rename is part of the atomicity assumption.

The project run lock is an OS advisory lock (`flock` on unix, `LockFileEx` on Windows) held on the open `lock.json` handle for the life of the process. The kernel releases it on process exit, so an interrupted run cannot leave a project permanently locked; the next run reclaims a leftover `lock.json` after finding no live lock on it. `lock.json` records the run ID, PID, and an owner token as diagnostics only. Once a run is `FINALIZED` (or a `recover` action has completed), a failure to delete `lock.json` is reported as a warning on a finished run, never as `RECOVERY_REQUIRED`.

Apply verifies every generated file's SHA-256, then runs the plan's declared validations, and only then marks the run `FINALIZED`. An unknown validation ID fails closed. A validation failure rolls back exactly the files the run created whose bytes are unchanged, identical to a hash mismatch.

Approval timestamps are checked against the run window: `approved_at` may not precede the run start by more than one second and may not lead the engine clock by more than `clockSkewAllowance` (5 minutes). The forward allowance only absorbs benign wall-clock skew between the approving and applying machines; it is not a validity window and does not extend how long an approval can be used.

REINITIALIZE stays disabled until backup fidelity, local recovery indexing, locking, fault injection, and supported-platform integration tests all pass. Permanent deletion and Git-history removal remain separate advanced approvals.
